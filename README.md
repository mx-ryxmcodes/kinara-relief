# Flood relief coordination dashboard (Sindh)

One shared dashboard for flood-relief camps, their needs, warehouse inventory, dispatches, donations and volunteers. It stops duplicate or excess deliveries and puts the worst gaps first. Built from the PRD: React + Vite on the front, a small Node server (`server/server.js`, no extra dependencies) as the API.

All names, quantities and amounts in the seed data are fictional demo data.

## Run it in VS Code

You need Node 18 or newer.

```bash
npm install
npm run dev:all        # API on http://localhost:3001 and the app on http://localhost:5173
```

Or in two terminals: `npm run api` and `npm run dev`.

| Command | What it does |
| --- | --- |
| `npm run dev:all` | Starts the API and the app together |
| `npm run api` | The Node API on port 3001, serving `db.json` |
| `npm run api:json` | Plain JSON Server on port 3001 instead (the app still works; actions then run in the browser) |
| `npm run dev` | Vite dev server |
| `npm run seed` | Resets `db.json` to the seed data (stop the API first, or it reloads) |
| `npm run check:seed` | Checks `db.json` against the brief's counts and the consistency rules |
| `npm run user -- list` | Lists the sign-in accounts (see Accounts below) |
| `npm test` | 100+ tests: rules, actions, server security, and every page |
| `RELIEF_USER=... RELIEF_PASSWORD=... node scripts/integration.mjs` | End-to-end check against the running API (restores the data it changes) |
| `npm run build` | Production build into `dist/` |

To host it, see `DEPLOY.md` (one Render service serves the app and the API).

To point the app at another API, copy `.env.example` to `.env` and set `VITE_API_URL`.

## How it is organised

```
db.json                 seeded data, served by JSON Server (generated by npm run seed)
server/seed.js          the seed dataset (8 camps, 12 items, 20 needs, 10 dispatches, 10 donations, 15 volunteers)
server/server.js        the API: REST routes plus all-or-nothing /actions
server/check-seed.js    verifies counts, mixes and consistency
src/api/client.js       the only file that talks HTTP
src/logic/rules.js      pure rules: camp status, low stock, available stock, progress, gaps, KPIs
src/logic/validators.js form validation
src/logic/actions.js    every write, with the checks that protect the data
src/logic/permissions.js  role matrix
src/pages/              Dashboard, Camps, CampDetail, Inventory, Dispatches, Donations, Volunteers
```

Derived values (Low Stock, available stock, progress, gap, Full status) are computed in `rules.js` and never stored, so screens cannot disagree. To move to Supabase later, only `src/api/client.js` needs to change.

## The rules that matter

- **Reservation.** Creating a dispatch reserves stock at once. Physical stock only drops when the dispatch is marked Delivered, so available stock is stock minus Pending and In Transit dispatches.
- **Dispatch limit.** A dispatch cannot exceed available stock, or the need's remaining unreserved quantity (required - fulfilled - other Pending and In Transit dispatches).
- **Lifecycle.** Pending, then In Transit, then Delivered. Pending or In Transit can be Cancelled, which frees the reservation. Delivered and Cancelled are final.
- **Camps.** A camp becomes Full when families reach capacity and returns to Active below it. Closed is manual. Closing a camp unassigns its volunteers.
- **Volunteers.** One camp each, never a Closed camp.
- **Dashboard.** Critical gaps are High priority needs under 40% fulfilment at open camps, worst first. Overall and per-category fulfilment average each need's progress, so a small need counts as much as a large one. Underserved camps are ranked by a priority-weighted gap (High 3, Medium 2, Low 1).

## Roles

A selector in the sidebar switches between Relief Coordinator and Field Volunteer. It follows the PRD's matrix: volunteers can update a camp's families and mark In Transit dispatches Delivered, and otherwise view. This only hides controls. There is no login and JSON Server has no authentication, so do not use real data.

## Known limits

- **Concurrency.** The Node server handles one request at a time, and every action runs all or nothing: if anything fails part way, the data is put back exactly as it was. Two people acting at the same moment cannot over-reserve stock. This holds for one server process on one data file. Direct REST writes (for example `POST /camps`) skip the app's rules, as they did with JSON Server.
- There is no authentication, and the data file lives with the server. If you deploy it, host the API on a Node service (not a static host); on hosts with temporary disks the data resets to the seed on restart.
- Donations are add-only (no edit or delete), because reversing an In-Kind donation would have to reverse stock.

## Accounts and sign-in

Nobody can see or change data without signing in. Accounts live in `server/users.json` (passwords are stored only as scrypt hashes). The server checks the role on every request, so a Field Volunteer cannot add camps, dispatch, or edit stock even by calling the API directly.

```bash
npm run user -- list
npm run user -- set coordinator "a-new-long-password"
npm run user -- set asma "her-password" --name "Asma Khoso" --role volunteer
npm run user -- remove asma
```

Passwords need at least 8 characters. Five wrong tries lock that ID out for 15 minutes. Sessions last 8 hours. Restart-proof sessions need a fixed `SESSION_SECRET` environment variable (see DEPLOY.md).
